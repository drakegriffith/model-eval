# GLM 4.7 placement record (2026-08-26)

## Part 1: Where GLM 4.7 lands (2026-08-26)

Zoom out: the stack ranks coding models by pass rate on a five-tier task gauntlet (t1 easy to t5 hard) at a stated cost, run through the same claude-code driver. GLM 4.7 is the local model (LM Studio on the Studio, 131072 context, one request at a time). Until today it had no scored row: every request died at about 200 s because the claude-code client gave up waiting while the server was still thinking (issue #40, fixed by PR #44).

Evidence now on file (stage-0 probe, issue #8 comment of 2026-08-26): 5 of 5 reps of t3-a (the middle tier, a CLI-build task with an acceptance suite) passed, 0 flips, at effort high, bare (no harness), K=20 acceptance cap never approached (max 1 request). Turns 43 to 84, wall 16 to 81 minutes, output tokens 5.7k to 38k per rep, decode about 9 tokens per second.

Like-for-like on the same task (exit ok rows in runner/results/results.jsonl): fable medium bare 1/1 pass in 4 turns and 49 s; sol low bare 2/2 in 1 turn and 50 to 74 s; hybrid medium harness 2/2 in 9 to 12 turns and 202 to 298 s.

Placement: on correctness at the middle tier GLM sits level with the cloud models, because t3-a is saturated (every model passes it) and cannot separate them. On cost class it sits alone: hours per task where the cloud models take minutes, 16x to 100x the wall time and 6x to 18x the output tokens, at zero marginal dollar cost. Analogy: a free contractor who finishes the same kitchen in a week instead of an afternoon. Concrete instance here: rep 1 spent 53 minutes inside one reasoning turn (28k tokens) before writing code.

What this does not say: nothing about t4 or t5, where a model can fail rather than merely be slow; nothing about harness levels; nothing at effort low or medium. Those are stage 1's questions.

Options for stage 1 (runner/runs-glm-stage1.yaml, reps now 2 per A6, N=260 per A3): (a) run it as registered, sequential, at about 40 minutes per GLM row on t3-a and longer on t4/t5, so budget roughly 20 to 30 hours of Studio time and accept that a stalled night loses a day; (b) cut to t3 to t5 only, which keeps the tiers that can separate models and roughly halves the clock; (c) stop at stage 0 and publish the placement above as "middle-tier parity, hours-not-minutes cost class".

A second number bears on all three options: `serving_registry.derive_wall_clock_s(260)` (the A3 formula: N x 157 x 1.5, rounded up to the next 600 s) evaluates to 61800 s, about 17 hours. That is the per-row hang backstop stage 1 would now run under before a stuck GLM row gets called a timeout, not an estimate of typical wall time (stage-0 rows finished in 16 to 81 minutes) -- it is how long one stalled row is allowed to sit before anything notices. Also unresolved as of this writing: `runner/runs-glm-stage1.yaml`'s stage-1 primary arm still declares `reps: [1, 2, 3]` on origin/master, while amendment A6 (5/5 identical, 0 flips) says stage-1 reps should be 2. No commit has reconciled the two; that is a pending Drake decision or a follow-up commit, not yet the recorded state.

Recommendation: (a) with a stated wall-clock budget, because the placement question Drake asked is answered only where GLM can fail, and stage 0 shows the pipe now holds. The one fact that flips it: if the first t5 row on GLM exceeds the 7200 s backstop (exit_reason timeout), the estimand excludes it and stage 1 as registered cannot place GLM at the top tier; then choose (b).
